# 全站 PDF 阅读兼容与性能优化

日期：2026-10-19（Asia/Shanghai）。基线为 GitHub main `300c754`；用户明确要求全站优化并上传仓库，沿用既有公网预览站。公共责任人 00；构建／发布责任人 10。iGEM 官方仓库和官网未改动，首页视频按用户叫停要求保持。

## 实际改动

1. IHP、Hardware、Software、Education 统一自托管 PDF.js 阅读器，覆盖 46 份不同 PDF、311 页。旧 PDF、页面文字、图表、锚点和原文件入口保留。
2. 仅展开且靠近阅读位置的文档加载，每页最多运行两个阅读器；收起或移远后释放 iframe、worker、画布。重新打开恢复页码、缩放和 PDF 页内坐标。Hardware 四份指定文档、Education 23 份方案保持默认展开；其余默认状态保持。
3. 使用同版 5.6.205 官方 legacy 压缩库，保留兼容补丁和 Apache 许可。核心与 worker 从 3,357,952 字节降至 1,789,872 字节，源码体积减少 46.7%；这是未压缩源码大小，不等于实际网络传输量或加载时间降幅。
4. 在打开的阅读器内并行发现公共模块和 PDF；禁用整本文档页面的后台预初始化，在服务器支持时按需分段请求。手机／桌面的单画布像素上限分别为 4／8 兆像素。保留文本选择、链接、翻页、缩放、适宽、原件打开、失败重试和键盘操作。
5. 阅读器不再只允许 IHP 路径，支持全站同源 PDF，包含中文和空格路径。内部脚本、字体等采用相对路径；未来迁移 iGEM 时仍需适配实际媒体域名和官方构建，未宣称可原样迁移。
6. PR #17 公网核验补充发现旧 `reading-return.js` 的 Back 预留宽度在桌面缩至手机时会异常累加：Education 实测达到 1442px，正文被压至 38px，PDF 框只剩 2px。将普通正文／居中 Team 的预留上限分别设为 50／100px，避免把响应式切换过程的暂时溢出当作永久留白；保留框外按钮和原返回行为。

## 验证结果

- 四个有 PDF 的页面共 74 处阅读入口：IHP 14、Hardware 8、Software 2、Education 50；与基线完全一致。默认展开数量分别为 0／4／0／23。
- Education 页面初入时 PDF 请求从 23 个降为 0；四页入页均不请求 PDF 或阅读器文件。只有接近展开的文档时才启动阅读器。
- Chrome 禁用原生 PDF 预览后，46 份原 PDF 的首页和末页全部显示，合计 311 页，包含中文指南、盲文及图片型手册。
- 从盲文第 40／56 页放大后收起，再打开恢复第 40 页、缩放和页内坐标；收起后 worker 为 0。Education 跨五处资源位置连续滚动，运行中的阅读器和 worker 均不超过两个。
- Chrome 390／1440px 阅读器截图检查通过。Edge 390px 检查 22 个目录内 HTML 入口，无整页横向溢出、无脚本错误；Software 的键盘展开、上一页／下一页和原文件入口通过。根入口另外由构建资源检查验证，23 个 HTML 均在产物中。
- 正式构建和资源检查通过：23 个 HTML、1266 个文件，无缺失／超限／不安全文件。没有新增运行时依赖、外部文档服务或修改 CI、部署凭据、发布开关。
- 留白补正后，22 个目录内 HTML 入口逐一从 1440px 缩到 390px、再恢复桌面，没有异常预留值或整页横向溢出。Education PDF 框在缩窗后从故障时的 2px 恢复为正常 228px；四个 PDF 页面及 46 个原件地址的正式构建本地验收全部通过。Education 两个宽度的 Back 按钮均在框外且不越过视口，点击返回原 1800px，偏差 0px。详见 [响应式验收记录](verification/pdf-responsive-gutter-20261019.json)。

## 性能边界

本地 Chrome 同一 60ms 延迟／10Mbps／CPU 2 倍限制条件下，各三次冷启动，首屏等待中位数约由 1.62 秒至 1.64 秒，没有测出稳定的首次显示提速。主要已验证收益是消除 Education 入页时的 23 个 PDF 加载、压缩公共代码，以及避免多个文档持续占用内存；不把源码压缩比例当作打开速度提升比例。

抽查当前公网 PDF 端点没有返回可用的 byte-range 支持，因此现阶段仍可能下载完整 PDF；本地预览同样按完整读取回退。`disableAutoFetch` 仍会阻止 PDFViewer 预先初始化所有页面。没有通过伪造响应头强行开启分段读取，也没有为了优化改写原 PDF。
